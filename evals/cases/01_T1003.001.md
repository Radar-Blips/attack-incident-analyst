## What a good report must say

- Multiple independent methods were used to dump LSASS memory.
- Two separate domain controllers, two separate dates about three months apart.
- Dumpert indicates an attempt to evade EDR user-mode hooks (direct syscalls). Frame it as attempted evasion: kernel callbacks and ETW-TI still see it, as the Sysmon EID 10 here shows.
- Run B used a renamed procdump (masquerading).
- Run B includes an interactive Task Manager dump, unlike the automated run A.
- LSASS dumping on a DC needs admin rights, so privileged access was already held.
- Mimikatz and pypykatz were executed, but their success is not proven by this telemetry.
- Acceptable (credited, not required): artefacts (`C:\AtomicRedTeam\`) are consistent with Atomic Red Team, so authorisation should be confirmed.

## What a good report must NOT say

- Splunk Universal Forwarder activity as suspicious or part of the incident.
- Atomic Red Team staging (prerequisite checks, installs) or cleanup as confirmed attacker actions.
- Defender or EDR access to LSASS as malicious.
- That pypykatz extracted credentials.
- That Mimikatz parsed a dump created in this dataset, or the Task Manager dump specifically (different host, different date).
- That one tool parsed another tool's dump.
- That both runs were on the same host, or one continuous intrusion.
- Lateral movement between the two DCs.
- That the attacker gained domain admin through this activity (it was a precondition, not an outcome).
- That credentials were confirmed stolen or exfiltrated (dumps were written; extraction and exfiltration are not proven).
- That the activity is benign and can be closed because Atomic Red Team was used (ART can be used by real attackers; authorisation must be confirmed).
- That opening Task Manager, or its routine low-privilege LSASS queries (0x1000, 0x1400), is malicious; only the 0x1fffff access plus the dump write is.
- That Dumpert went undetected: it bypasses user-mode hooks, but Sysmon still logged its LSASS access (EID 10).

## Executive summary

LSASS memory was dumped on two separate domain controllers, three months apart, using several methods including EDR-evasive (direct syscalls bypassing user-land hooks) and renamed tools; artefacts are consistent with Atomic Red Team tooling, so confirm whether this was authorised testing. Dumping LSASS on a DC requires privileged access that was already held, and any credentials in memory on those DCs, potentially including KRBTGT, must be treated as exposed. If not authorised, reset exposed credentials and reset KRBTGT twice, allowing for replication and ticket lifetime between resets.

## Recommendations (acceptable, not scored as required)

- Confirm with the red team or BAS owner whether the activity was authorised.
- If not authorised: treat credentials in memory on both DCs as exposed and reset them.
- Reset KRBTGT twice, waiting for replication and at least the maximum ticket lifetime between resets (10 hours by default).
- Credit a report that recommends credential reset including KRBTGT; do not require the exact procedure.

## Scoring notes

- Technique precision and recall use the tiers above: required missed = fail; acceptable = neutral; wrong = false positive.
- Factual accuracy: each "must NOT say" item present in the report is a hallucination or overclaim.
- Run coverage: a report that covers only run A misses T1036.003 and the Task Manager dump.
- Outcome claims: "succeeded" only where a dump-file write or an LSASS access event proves it.
